# 个人信息保护影响评估（PIA）—— Drift，2026-09-27

**留存期：本文件与其处理情况记录留存不少于 3 年（个保法第五十六条第二款），至少保留到
2029-09-27。** 留存的对象不只是这份报告，还包括每次处理活动实质变化时新增的评估 ——
覆盖式修改会让「当时是按什么评估通过的」不可回答，而那正是第五十五条要求事前评估的
理由。

## 为什么必须做这次评估（适用性判断）

个保法第五十五条列举了四类必须事前评估的情形，本项目至少落入其中三类：

| 情形（第五十五条） | 是否落入 | 事实依据 |
|---|---|---|
| 处理敏感个人信息 | **是** | 陪伴聊天的对话正文高概率包含健康（含精神健康）、性取向、宗教信仰等敏感个人信息，见第 4 节 |
| 利用个人信息进行自动化决策 | **是** | 危机风险分级（`safety_event.risk_level`）与依赖信号（`dependency_signal`）是对个人的自动化判定，并会改变服务行为 |
| 委托处理、向他人提供、公开 | **是** | 对话正文与人格提示词被委托给境内 LLM provider 处理（第 5 节）；二级危机会向运营者披露「某用户触发了危机」这一事实 |
| 向境外提供个人信息 | **否** | 境外通道在类型层只接受合成文本（`callFrontier(readonly SyntheticText[])`），真实用户原文在编译期传不进去；`packages/llm/src/hosts.ts` 的三张互斥 host 表加启动期断言保证境外 host 只服务该角色 |

⚠️ **把「研究性质」当成适用范围抗辩的说法在本文件中不存在，也不得出现在任何对外文案
里**（PROJECT.md 的永久排除项、UI-SPEC〔禁用〕规则 3；被禁的是那句话本身，所以这里刻意
不把它写出来 —— 写出来会让扫描它的那条断言被自己的说明命中）。规模抗辩
（`compliance/publicness.json` 的四项状态）只对《人工智能拟人化服务管理办法》第二条的
适用范围有意义；**个保法没有小规模豁免**。

## 1. 处理目的与方式

处理方式：单机 Docker Compose 部署，PostgreSQL 18 为唯一真相源，任务队列与 OLTP 同库
（pg-boss 独立 schema）。对话经单条 WebSocket 传输，全部生成内容在落库前经出站安全
网关（`packages/safety`），角色消息的 AI 明示标识在落库那一刻注入且不接受调用方传参，
数据库层另有 CHECK 兜底。

⚠️ **本节与 `DATA_INVENTORY` 的关系**：`packages/db/src/inventory.ts` 的 `DATA_INVENTORY`
是 PRIV-03 / PRIV-05 / PRIV-08 的共同真相源，由 Plan 10 落地。它落地时，本节的逐表清单
必须按它重新导出并复核 —— 两份清单不一致时以 `DATA_INVENTORY` 为准，因为它是被 CI 断言
守着的那一份（新增列不登记即构建失败）。当前逐表清单直接依据 `packages/db/src/schema/`
的 22 张表编写。

| 表 | 处理目的 | 是否个人信息 | 保存期 |
|---|---|---|---|
| `user` | 账号标识与登录 | 是 | 账号存续期 |
| `account` | 凭据（scrypt 派生，不存明文口令） | 是 | 账号存续期 |
| `session` | 登录态（不透明 token） | 是 | 会话有效期 |

| `invite_code` | 一次性准入凭证；`used_by` 是注册用户数的唯一可信来源 | 是（`used_by`） | 码本身是运营资产，长期；一键删除时 `used_by` 置空 |
| `consent` / `consent_event` | 五项同意的当前状态与变更留痕（合法性基础本身） | 是 | 账号存续期 + 变更留痕 |

| `safety_event` | 危机识别结果与分级（自动化决策的留证） | 是 | 6 个月（合规留存），一键删除时去标识化 |
| `session_risk_state` | 会话级风险状态机 | 是 | 会话结束后短期 |

| `usage_segment` | 连续使用时长（COMPLY-03 的服务端计时依据） | 是 | 6 个月 |
| `llm_call` | 每次 provider 调用的可观测底座（PLAT-08） | 间接（含 `input_hash`，不含正文） | 6 个月 |
| `privacy_action` | 导出/删除等隐私动作的回执与留证（PRIV-04/05） | 是 | 6 个月 |
| `client_error` | 前端异常上报（D-28） | 可能间接 | 6 个月 |

处理目的的边界有三条，它们是设计约束而不是承诺：

1. **不做模型训练**：不对任何模型做微调或权重更新。人格演化是**状态更新**（写
   `persona_version` / `character.state`），与训练在实现上是两件事 —— 但见第 3 节末的
   不确定性登记 ②。
2. **不做广告与画像营销**：无第三方 SDK、无广告标识符、无跨站追踪。
3. **日志是白名单式的**：`apps/api/src/obs/logger.ts` 只允许白名单字段落盘，`logError`
   只取 `error.name`（不取 message 与 stack，因为 pg 的报错串里可能带 SQL 参数，而参数
   就是消息正文）。日志文件不能按行删除，PRIV-05 的级联到不了它，唯一诚实的姿态是从
   设计上不含个人信息。

## 2. 对个人权益的影响与安全风险

| 风险 | 影响 | 可能性 | 缓解措施（已实装的与尚未实装的分开写） |
|---|---|---|---|
| 对话正文泄露 | **严重** —— 高概率含敏感个人信息 | 低 | 已实装：单机部署、PostgreSQL 不对外暴露、compose 的 api/web 端口默认只绑回环（`API_BIND` / `WEB_BIND` 默认 127.0.0.1）、对外入口只有 caddy |

## 3. 保护措施的合法性有效性

评估结论：**保护措施与处理目的相适应，但其有效性依赖「门先于撤」——**即保护措施必须是
机械的、会失败的检查，而不是写在文档里的约定。逐条说明：

| 保护措施 | 合法性依据 | 有效性判据（机械的那一条） |
|---|---|---|
| 五项同意（两必选三可选） | 第十三条第一款、第十四条、第二十九条 | 同意项与数据流锁步：某项被撤回则对应条目从隐私中心列表消失；无数据流的同意项不得渲染成「我们收集了…」 |
| 敏感个人信息单独同意 | 第二十九条 | `consent.sensitive_pi` 为独立必选项，不与基础服务捆绑在同一个开关里 |
| 出站安全网关不可绕过 | 第九条（安全保障义务） | branded type：出口签名只接受 `GatedText`，`as GatedText` 全仓只允许出现在唯一产出点，`EGRESS_POINTS` 注册表与 AST 扫描结果集合相等 |
| AI 明示标识 | 《标识办法》第四条、第九条 | 标识不作为参数传入 + DB CHECK 兜底：新增一条绕过标识注入的写入路径在数据库层失败 |
| 最小必要与目的限制 | 第六条 | 日志白名单；告警载荷类型体内不存在文本字段；`llm_call` 落 `input_hash` 而非正文 |
| 保存期限最短必要 | 第十九条 | 保存期写在 `DATA_INVENTORY` 的 `retention`（Plan 10），清理作业由它生成而不是另写一份 |
| 委托处理 | 第二十一条 | 路由表里每个**已启用**的 provider 都必须在 `compliance/dpa/` 有一份含 `data_used_for_training: false` 与配置证据的协议，否则构建失败 |
| 个人权利（查阅/复制/删除） | 第四十五条、第四十七条 | 未实装（Plan 11）：导出与一键删除加「N 处存储」回执 |
| 研究库不得含原文嵌入 | 第六条、第九条 | `db/publication/research_publication.sql` 是唯一真相源，裸表名或向量列即构建失败（RES-02/03），两个假 SQL 证明该扫描非空真 |

### 显式登记的两项不确定性

这两项都**无法**在本轮内定论。登记它们的理由与 `SKIPPED_CHECKS.md` 相同：一个没有被
写下来的不确定性，会在它变成问题的那一天被当作「当时没想到」。

**① GB 45438-2025 文本类隐式标识在纯文本导出上的形态不明（Confidence: LOW）**

- **现状**：《人工智能生成合成内容标识办法》区分显式标识与隐式标识；隐式标识要求添加在
  文件数据中、不易被用户感知。图片、音频、视频有成熟的元数据/水印载体，**纯文本导出
  （`.md` / `.json`）的隐式标识载体形态在标准原文中的确切要求，我们尚未向标准原文复核**。
- **Phase 1 的做法（显式标识，不声称是隐式标识）**：导出文件头三行元数据块 + 每条角色
  消息正文加 `[AI] ` 前缀。前缀而非后缀、写进正文而非依赖查看器渲染 —— 导出文件会离开
  本平台，任何依赖平台侧渲染的标识在那一刻就消失了。
- **为什么不猜一个隐式标识形态**：猜错的代价不是「少做了一件事」，而是**声称做了而实际
  没做**。因此本项目在对外文案中只声称「显式标识」，不声称隐式标识已落实。
- **解除条件**：向 GB 45438-2025 标准原文复核文本类隐式标识的载体要求；若要求存在，在
  导出路径落地并重新评估本节。**公开前必须完成此项复核。**

**② 全局人格演化是否构成《办法》第十六条第四款的「模型训练」（Confidence: MEDIUM）**

- **现状**：技术上不构成 —— 不更新任何模型权重，人格演化写的是数据库里的状态。但法条
  规制的对象是「用户的敏感交互数据被吸收进一个持续存在、服务于他人的系统状态」，而全局
  人格完全符合这个描述，且**比微调更甚**：微调的影响被稀释在数十亿参数里，而人格档案
  里的一句话是直接可读、可被其他用户看到的。
- **本项目的选择：按「构成」设计。** 具体落点：(a) 演化参与在五项同意里是一个**独立的
  可选同意项**，不与基础服务捆绑；(b) 人格变更可归因、可减除（`persona_version` 不可变
  链 + 冻结 baseline + 「变更 ↔ 输入来源」反向索引），撤回同意时能从最近一个干净快照
  重算，而不是只能「以后不再用」；(c) 在技术文档中显式区分「人格演化（状态更新）」与
  「模型训练（权重更新）」，并留存不做微调、不向 provider 传训练标记的配置证据。
- **已知张力（如实登记）**：全局人格的本质是「一个用户的影响会流向所有用户」，而删除权
  与撤回权的本质是「一个用户的数据影响应当可被移除」。**这两者不可能完全兼容**，只能靠
  「可减除 + 定期快照回滚」把不兼容压到可接受范围。这是全局人格的真实代价之一。
- **解除条件**：监管口径明确，或本项目改为按用户隔离人格。届时重新评估 (a)(b)(c) 是否
  仍然必要。

## 4. 敏感个人信息说明

**结论：陪伴聊天的对话正文必须按敏感个人信息对待，因此收集它需要第二十九条的单独同意
（`sensitive_pi`），而不是包含在基础服务同意里。**

理由不是「可能会有」，而是**这类产品的核心使用场景就是它**：用户找一个角色聊的恰恰是
不方便对身边人说的事 —— 情绪低落与精神健康状况、亲密关系与性取向、宗教信仰、疾病与
就医经历、家庭冲突与经济困境。第二十八条把生物识别、宗教信仰、特定身份、医疗健康、
金融账户、行踪轨迹列为敏感个人信息，并把「一旦泄露或者非法使用容易导致个人尊严受到
侵害或者人身、财产安全受到危害」作为判据。对话正文在这个判据下是典型的敏感个人信息。

由此推出四条执行约束：

1. **单独同意**：`sensitive_pi` 是一个独立的必选同意项，注册页与隐私中心各有独立开关；
   撤回它等于停止服务并删除数据（Q2 裁决），而不是「撤回后继续聊天」。
2. **不得用于与该目的无关的处理**：对话正文不进任何统计分析、不进研究库原文层。
3. **告知必须具体**：不得用「为了改善服务」这类无指向的目的表述。
4. **未成年人**：不满十四周岁的个人信息属敏感个人信息且需监护人同意（第三十一条）。
   Phase 1 无公开注册入口、准入是一次性邀请码的熟人范围，因此**未成年人模式尚未实装**
   并在 `compliance/CHECKLIST-2026-09-27.md` 中如实裁决为 `not_applicable`；一旦
   `public_signup_entrance` 转为 `true`，该裁决即不再合法。

另有一类第三方敏感信息：`emergency_contact` 里的紧急联络人。该第三方从未与本平台建立
关系，也无法在本平台行使权利。Phase 1 已建表但**尚无写入路径**；Plan 07 接入前必须先
回答「如何向该第三方履行告知义务」，否则不得启用。

机械保证（`tools/ci/compliance-docs.test.ts`）：

- 路由表里出现的每个 provider（`mock` 除外）都必须在 `compliance/dpa/` 有对应文件 ——
  新增一个 provider 而不登记即构建失败；
- **已启用**（`enabled: true`）的 provider，其协议必须含 `data_used_for_training: false`
  与配置证据章节 —— 未签 DPA 的 provider 不得被启用；
- 反向断言：`compliance/dpa/` 下不得有孤儿文件（协议对应的 provider 已从路由表移除时，
  这条会提醒去复核而不是让文件默默留着）；
- 负向 fixture：给同一检查函数喂一个含不存在 provider 的假路由表，断言抛错并点名该
  provider —— 否则这条断言在「只有四个 provider 且都已登记」时是空真的。

**为什么按 `enabled` 分级而不是一律要求已签**：`PLAT-05` 不允许路由表留空洞，所以表里
必然存在尚未启用的角色与 provider（第一次用到时临时配一个会绕过全部启动期断言）。而
委托处理**在真实调用发生时才发生**：一个 `enabled: false` 的条目不处理任何个人信息。
把「必须已签」的判据绑在 `enabled` 上，既不虚构一份没签的协议，也不给未签的 provider
留放行口子。

## 评估结论

1. 处理目的明确、方式合法，对个人权益的影响**可控但不可忽略**，主要风险集中在对话正文
   的泄露与出境、以及危机识别的漏判。
2. 已实装的保护措施与风险相适应；**尚未实装的部分已逐条如实标注**，且都有一个会失败的
   检查或一条登记（`SKIPPED_CHECKS.md`）守着它不被忘记。
3. 两项不确定性（GB 45438-2025 文本类隐式标识形态、人格演化是否构成模型训练）已显式
   登记并各自给出解除条件。第 ① 项是**公开前的阻断项**。
4. 处理活动发生实质变化（新增数据流向、新增 provider、四项公开性状态任一变化、研究管道
   上线）时，必须重新评估并新增一份评估报告，而不是修改本文件。
